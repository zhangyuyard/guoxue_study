## 二、症状 ②：打开大书过久（已修）

### 2.1 复现与量化（修复前）

| 书 | 字节 | tap→正文可见 | 斜率 |
|---|---|---|---|
| 大学 | 7,503 | 1.38s | — |
| 史记 | 1,873,686 | 4.34s | 1.59 s/MB |

⇒ 耗时与字节**强线性 ≈1.5 s/MB**。开书期间 UI 树只有 **3 个节点**（顶部章栏 + 「已是第一章」+「‹ 返回」），**正文区 0 行**（逐时间点 dump：t=1.0/3.5/6.0/9.0/12.0s 均如此，t=15.0s 才出现 29 节点）。

### 2.2 根因

阅读器装载走的是 `ensureBookLoaded`（`src/services/UserBookService.ts:1081`）→ `loadBuiltinBookBody` —— **整本读取 + 全文解析完才 resolve**。

而为阅读器写的「首章优先快速水合」`ensureBookReady`（同文件 **:2170**，其文档注释原文即「**阅读器专用入口，问题：首开加载圈太长**」）走 meta 按章切片（`hydrateBuiltinViaMeta`，:2093），只读目标章的字节区间 —— 但**生产代码零调用**，只有 2 个测试文件引用：

```
$ grep -rn "ensureBookReady" src/ --include="*.ts" --include="*.tsx"
src/__tests__/ftsBookChunkYield.test.ts:400,451,485 …
src/services/__tests__/UserBookService.builtinResilience.test.ts:507,515,551,560,940,973 …
src/services/UserBookService.ts:2170   （定义）
src/services/UserBookService.ts:6010   （聚合导出表成员）
```

meta 资产齐备且指纹匹配：《资治通鉴》`tongjian.meta.json` 的 `sizeBytes = 9473320` 与 `tongjian.txt` **逐字节相同**，294 章各带 `s`/`e` 字节区间 ⇒ 快路径条件本可满足。

### 2.3 被排除的假设（反证）

开书窗口内 logcat 显示 FTS 后台索引队列正在跑，且数值**高度吻合**：

```
14:47:00.657  [PERF][library] tap book=tongjian
14:47:30.747  [PERF][asm] paused reason=ftsCheckpoint gate=off
14:47:42.215  [PERF][fts] zuozhuan   parse=ok +3942ms
14:47:46.901  [PERF][fts] shiji      parse=ok +4419ms
14:48:02.342  [PERF][fts] tongjian   parse=ok +15173ms   ← 与白屏 16.24s 几乎相同
```

⇒ 极易判成「FTS 抢占 JS」。**对照实验否掉了它**：冷启后等 FTS 队列**真正跑完**（判据＝`[fts] parse=ok` 行数连续 3 次采样不再增长；实测在 +115.9s 达 77 本后稳定，等待 134.2s），再点《资治通鉴》⇒ 白屏仍 **15.82s**。
同理《史记》FTS 4419ms ↔ 白屏 4.34s 的吻合也属巧合。**（铁律 5：一个观测面能被多处改动解释就不能当判据。）**

### 2.4 修复

`src/screens/ReaderScreen.tsx` → `loadChapterData`：

1. **改走首章优先快速水合**（:163）：
   ```ts
   const ensure = await UserBookService.ensureBookReady(bookId, {
     priorityChapterId: cid,
   });
   ```
   同时传入正在装载的章 id（传 `null`/常量会让快路径去装配第一章，跳章首屏依旧空白）。
2. **空壳章兜底**（:175–:188）：首开只装配目标章，其余为「空壳章」（segments 为空）。若取到的章 segments 为空 ⇒ 调 `UserBookService.degradeChapterToWholeRead(bookId, cid)`（该出口 `UserBookService.ts:5942`，语义「整章直读、全有或全无」，其内部自行从 meta 取字节区间，不依赖壳登记）⇒ **重取一次**章数据；仍空则抛「章节正文加载失败」（不静默渲染空白页）。

未改动：`ensureBookLoaded` 及其它消费者（背诵练习页、笔记列表页）保持整本水合语义。

### 3.2 探针取证（事件级）

给 `ScrollMode.tsx` 注入 5 处临时探针（`[DBGJ]` 前缀），**开书后 0.2s 立即**开始随机滚动 40 步（覆盖首帧窗口），并用「按住来回拖」再跑 8 组：

| 探针 | 随机滚动 40 步 | 按住来回拖 8 组 | 判读 |
|---|---|---|---|
| `anchorLost`（锚行丢失 ⇒ 不补偿） | **0** | **0** | 视口锚点从不丢失 ⇒ 无「不补偿导致的跳变」 |
| `comp`（补偿量） | 6 | 9 | 见下逐轴核对 |
| `commit`（跨章提交） | 43 | 10 | 与手势方向/章节序自洽 |
| `bootRemount`（首帧重挂载） | 0 | 0 | 0.2s 内即交互 ⇒ `userScrolledRef` 先置位，重挂载按设计取消 |

**补偿算式逐轴数值核对**（`rowH ≈ 29dp`、`44` = 章界提示条高度）：

```
[DBGJ][comp] prevIdx=68 nextIdx=85 delta=449 off=2032 len=161 head=44→0
   (85−68)×29 + (0−44) = 493 − 44 = 449   ✓ 与日志 delta 逐轴相等
[DBGJ][comp] prevIdx=59 nextIdx=38 delta=-565 off=1716 len=140 head=0→44
   (38−59)×29 + (44−0) = −609 + 44 = −565 ✓ 逐轴相等（len 161→140 = 上方裁掉 21 行）
```

（算式即 `anchorCompensationDelta = (nextIdx−prevIdx)×rowH + (nextHead−prevHead)`，`rowH≈29dp`、`44` = 章界提示条高度。）

即：**数据位移量、头高变化量、补偿量三者互相吻合**，补偿按设计把视觉位置维持住；`off=3102 → y=2537` 的读数为补偿落地后的原生回执，与 `delta=-565` 精确对应（不是独立故障）。

### 3.3 本轮追加的三条仪器（针对前四条的量法盲区）

前四条都是**位移/状态型**判据（章号、墨量、行数、补偿量），对「内容错位但整体位移正确」与「开书头 2 秒」两种情形无检测力。故本轮新造三条**内容级/窗口级**判据，全部在**无探针正式包**（sha256 `57f4598264c1ef2c`）上跑：

| # | 仪器 | 判据（变异下会红） | 规模 | 结果 |
|---|---|---|---|---|
| 5 | `v17_seam.py` 内容连续切片 | 每帧可见正文行拼接后必须是**全书 CJK 串的连续子串**（`find>=0`）；且上滑 idx 必增、下滑必减。仪器自证：插原文外字必红、复制两行必红、真帧必绿 | 30 轮随机方向×幅度×时长 | **内容不连续 0 次 / 反向回跳 0 次**；`idx` 随方向严格单调（书首钳位处 Δ=0，符合预期） |
| 6 | `v18_openwatcher.py` 开书期位置监视 | tap 后 9 秒内高频采样位置，**无手势**下 `idx` 变化即「自跳」 | 9.0s，≈22 帧 | **位置变化 0 次**（首帧即 `idx=295`，此后恒 295） |
| 7 | `v19_jank.py` 帧级 jank（观感读法） | `dumpsys gfxinfo` 的 janky% / 百分位 | 静止 10s vs 滚 30 次 | **仪器失效**：本机 `Total frames rendered: 0`（见 §五 5） |

### 3.5 探针包量测：补偿落地时序（症状①的机理候选）

用户追问结果：观感＝**画面瞬移一段（净位移，不回原位）**；时机＝**随时都有**；不录屏。⇒ 追加第 8 条仪器：给 `ScrollMode.tsx` 埋 **6 处** `[DBGK]` 探针（`[y]` 每个 onScroll 的原生 `contentOffset.y`／`[end]` 动量结束／`[comp]` 补偿算式／`[apply]` 补偿落地／`[cs]` contentSize／`[skip]` 补偿待落定期间的早退），构建取证包（sha256 `3d68c00c637e15cc…`，包内 `DBGK` ascii=**6**）后驱动 40 次随机方向/幅度快滑（45 s）：

| 项 | 量值 |
|---|---|
| 事件计数 | `[y]` 2749 / `[end]` 31 / `[comp]` **61** / `[apply]` **116** / `[cs]` 37 / `[skip]` **31** |
| 补偿频率 | 61 次 / 40 次手势 ≈ **1.5 次/手势**（`apply` 为 `comp` 的 1.9 倍＝`useLayoutEffect` 与 `onContentSizeChange` 各投一次，与文件头 ④「首次投递被旧内容高钳制」一致） |
| 补偿量值域 | `delta ∈ [116, 629]` px（= 1.3–7 行；由 `(nextIdx−prevIdx)×29 + (head−prevHead)` 得来，与 §3.2 算式一致） |
| **静置自走** | 以 `[end]` 界定动量窗后，全 45 s **仅 1 个静置段（173 ms）**，其中 `y` 变化 **319 px**（同刻 2 `comp` + 4 `apply`，最大跳幅 **319.0 px**）⇒ **无手势时视口也会被程序化移动** |
| **补偿落地滞后** | 由 `[apply]` 到原生 `y` 首次进入 `target±1 行`：**中位 18 ms（≈1 帧）/ P90 62 ms / max 395 ms**；滞后 ≥50 ms 的 **28/116（24%）** |

**判读**：`scrollToOffset` 补偿落地前，内容相对屏幕被位移了整份 `Δ`（本次实测 116–629 px）。中位落地在 **1 帧**（不可见），但 **24% 的落地滞后 ≥50 ms**、最坏 ≈**0.4 s** ⇒ 与用户所述「随时都有、瞬移一段」的形状相符。

**必须声明的量法上限**：该滞后是用「原生 → JS `onScroll` 派发」测出来的，是**上界**；真实视觉暴露时间 ≤ 该值。要进一步分辨需 >60 fps 的像素证据，而本机 `gfxinfo` 与 `screenrecord` 双双失效（§五 5–6）⇒ **本机无法再往前一步**。按铁律 54（无真机读数不得改行为），本轮**不改**滚动逻辑。

**像素账目互核（第 9 条仪器，ZNCC 重算已存帧）**：无补偿区间的 `Δpix` 与 `Δoff` **逐对相符（中位残差 0.0 px）** ⇒ 像素与原生 offset 完全一致、相关器可信；含补偿区间用正确等式 `Δpix = Δoff − Σcomp` 复核，多数对残差 0.1/0.2/13.8 px（= 补偿在视觉上兑现），少数对偏离 160–325 px（受 ±375 ms 帧-日志对齐不确定度限制，不足以定性）。

> ⚠ **判据自身修正（两次同族，须记账）**：① `v22` 的「静置自走」窗口取 `手势 + ms + 400ms`，把**合法惯性**（高速 swipe 惯性可达 1–3 s）算成自走 ⇒ 20 个假违规；改用 `[end]` 定窗后降为 1 个真事件。② `v24` 的第一版直接要求 `Δpix ≡ Δoff` ⇒ 把**补偿正常工作**判成跳变（正确等式含 `−Σcomp`）；且 `MAXS=500` 使大位移真值退化成边界值 −500.0/+479.0（铁律 59① 的现场重演）。两次都是「仪器坏，非对象坏」。

## 五、本轮修掉的仪器缺陷（避免再犯）

1. **`bg` 解析**：旧脚本用 `split("bg=")[1].split()[0]` 得到 `(255,` ⇒ 与 `"(255,255,255)"` 比较**恒假** ⇒ `is_reader` 永为 False（真值 `ink=1236>1150` 却打印 False）。改为正则命名组。
2. **点错书而不知**：靠外部坐标点书时，冷启后书架回到「全部」分类 ⇒ `(852,1001)` 落到「中庸」上，却以为在测《资治通鉴》。改为**按书名文本自动定位** + tap 后用 logcat `tap book=<id>` **端到端断言**（不符则 `[TOOLFAIL] rc=3`，读数作废）。
3. **下滑起点触发系统手势**：起点 y=500 会拉出通知栏并令 App 失焦到桌面 ⇒ 读数变成桌面的假数据（曾读到「首=快捷启动 / 末=Brotato」）。改为 y=760 起，并在**每轮读数前再闸门一次** + 页面判据（章名非空且 ink>900）。
4. **逐像素位移估计的周期混淆**：正文行距实测 **≈92px**（自相关首个峰 d=23 样本），而原搜索范围 ±900px ⇒ 落进 ±92k 的假峰（表现为 Δy 恒 ±1020–1036、峰值与次峰几乎相同）。该法本轮**未用于结论**，改用「静置逐字判据 + 事件级探针」。
5. **`dumpsys gfxinfo` 在本机恒 0**：`Total frames rendered: 0`、`Janky frames: 0 (0.00%)`、直方图全 0、百分位读数为哨兵值 `4950ms`（reset 后静止 10s 亦然）⇒ 该机 HWUI 不采集帧统计（Huawei 定制）。**判为工具失效**（铁律 32），据此不得下「无卡顿」结论；`v19_jank.py` 已内置 `total==0 ⇒ [TOOLFAIL] rc=3` 早退。
6. **`screenrecord` 在本机不存在**：`/system/bin/sh: screenrecord: inaccessible or not found`（`/data/local/tmp` 与 `/sdcard` 两条路径均试）⇒ 「录屏→逐帧」路断。替代方案改为**用户手机系统录屏 + 本机 ffmpeg 分析**（ffmpeg 已就位）。
7. **`v18` 首版缺「点前必须书架」自证**：首跑首帧 `t=0.067s` 就有正文（比实测开书 1.39s 还快）＝典型假读数；补「点前截图 bg 必须 =(247,247,247)」+ 「tap 后 logcat 必须含 `tap book=<id>`」两道断言后，读数改为 `t=0.078s`（该值反映的是 **a11y 树可见**时刻，**不是像素可见**时刻；像素可见仍为 1.2–1.4s，两者不可混用）。
8. **`v17` 首版判据写漏**：`judge()` 只判了长度（`len>=20`）未判 `find(s)>=0` ⇒ **自证环节立刻红了**（插入原文外字仍 PASS）——正是「先造必须红的输入」这条纪律把缺陷挡在结论之前。修正后 S1/S2 皆红、S3 绿，判据才可采信。
9. **`v22` 的静置窗口把惯性算成自走**：窗口取「手势起点 + `ms` + 400 ms」，而高速 `input swipe` 的原生惯性可持续 **1–3 s** ⇒ 报出 20 个假违规。改用 `[end]`（动量结束）定窗后降为 **1 个真事件**。⇒ 教训：**判「静置」必须以「动量结束事件」定窗，不能以「手势时长 + 常数」推算**。
10. **`v24` 的判据等式缺项**：直接要求 `Δpix ≡ Δoff`，而**补偿正常工作恰恰使二者不等**（正确等式为 `Δpix = Δoff − Σcomp`）⇒ 把 31 对正常补偿判成跳变。⇒ 教训：**「两个量应相等」的判据必须先写全等式再比残差**。
11. **`v24` 的互相关量程外退化**：`MAXS=500` 时 `Δpix` 精准停在 **−500.0 / +479.0**（搜索边界）⇒ 量程外真值退化成边界值（铁律 59① 现场重演）；且未归一化 SSD 的重叠区变短会产生**假极小**（−1569/+1560）。改为 **ZNCC + 最小重叠比 0.6 + 粗到细搜索（±1000）** 后，无补偿区间残差中位 **0.0 px**。⇒ 教训：**互相关必须归一化并设最小重叠比，且必须带「静置 0 位移」的阴性对照**（本仪器：静置 7 s、18 对、0 违规）。
