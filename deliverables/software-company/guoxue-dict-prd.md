# PRD：国学学习 App 字典能力（原生字典 + 用户上传字典）

- **Language**: 中文
- **Programming Language**: React Native 0.74.7 + TypeScript + Zustand（沿用现有技术栈）
- **Project Name**: guoxue_dict_engine
- **文档版本**: v1.0（简单 PRD）
- **原始需求复述**：在现有国学学习 App 中增加原生字典（现代汉字词典、古汉语常用字字典等）与用户上传本地字典能力（兼容市面常见格式），并将字典中的多音字信息打通到多音字读音提示体系。原生字典须使用开源/公共领域数据，不得打包受版权保护的商用词典数据。

---

## 1. 产品定义

**一句话概述**：为国学学习者提供「开箱即查、可自行扩充」的离线字典引擎——内置合规的开源字典，支持导入 MDict/StarDict 等常见格式，并与多音字提示体系深度联动。

### Product Goals

1. **查得到**：内置字典覆盖现代汉字 8,000+ 字头、古汉语常用字 5,000+ 字头，离线可查、秒级响应（单字查询 < 50ms）。
2. **扩得动**：用户可导入市面主流格式的本地字典（MB 级），导入过程可解析、可取消、失败可恢复。
3. **联得上**：字典中的多音字读音与例句成为 PinyinService 多音字提示的数据来源之一，在阅读器中即时生效。

### User Stories

1. As a 国学学习者, I want to 在阅读典籍时点按任意字词即可查到现代义与古义 so that 我不需要切换到其他词典 App 中断阅读心流。
2. As a 进阶用户, I want to 导入我自己购买的 MDict（.mdx）或 StarDict 字典 so that 我可以使用更专业、更详细的词典内容。
3. As a 用户, I want to 在多个字典间切换查询同一字头 so that 我可以对照不同来源的解释加深理解。
4. As a 用户, I want to 配置「多音字读音来源」使用某个字典的多音字信息 so that 阅读器中的注音提示更符合我正在读的典籍的语言风格（古音/今音）。
5. As a 用户, I want to 在导入页看到解析进度、词条数与错误提示 so that 我能确认字典导入成功且知道失败原因。

## 2. 技术规范

### Requirements Pool

#### P0（Must have，首期）

| # | 需求 | 说明 |
|---|------|------|
| P0-1 | 原生「现代汉字字典」 | 基于开源/公共领域数据（Unicode Unihan + 通用规范汉字表等），8,000+ 字头，含拼音、部首、笔画、基本释义 |
| P0-2 | 原生「古汉语常用字字典」 | 基于公共领域数据（说文解字/康熙字典衍生开源数据等），5,000+ 字头，含古义、书证 |
| P0-3 | 统一字典查询引擎 | 单一接口：输入字/词 → 按当前激活字典（或全部字典聚合）返回释义；兼容现有 `DictionaryService` 调用方 |
| P0-4 | 字典存储层 | 原生字典与用户字典统一采用 SQLite（如 `react-native-quick-sqlite` / `op-sqlite`，由架构评审确定），建立字头索引，支持按需加载，避免将大数据打进 JS bundle |
| P0-5 | 用户导入：CSV / TSV / JSON / TXT | 纯文本格式解析导入（首期最通用、实现成本最低的自定义字典通道） |
| P0-6 | 用户导入：MDict（.mdx/.mdd） | 市占率最高，必须首期支持；解析字头索引与 HTML 词条内容 |
| P0-7 | 字典管理页 | 列出原生与已导入字典：启用/禁用、排序（决定查询优先级）、删除（仅用户字典）、查看词条数/大小 |
| P0-8 | 查字页（字典浏览） | 输入或从阅读器跳转：字头大字展示、拼音（含多音标注）、部首笔画、各义项分条展示、书证/例句、来源字典标签可切换 |
| P0-9 | 多音字打通（读） | 字典条目中的多音字读音与例句，作为 `PinyinService` 多音字判音的候选来源与提示示例 |
| P0-10 | 阅读器 → 查字典跳转 | ReaderScreen 点按字词可唤起查字页（Bottom Sheet 或页面跳转，沿用现有交互） |

#### P1（Should have，二期）

| # | 需求 | 说明 |
|---|------|------|
| P1-1 | 用户导入：StarDict（.ifo/.dict/.idx/.syn） | 常见开源格式，含 dictzip 压缩处理 |
| P1-2 | 多音字来源配置页 | 设置中指定「多音字读音来源」：内置规则库（现状）/ 某原生字典 / 某用户字典，并预览冲突时的优先策略 |
| P1-3 | 词条内链接与跳转 | MDict HTML 词条中的交叉引用（→其他字头）可在 App 内跳转 |
| P1-4 | 查询历史与生字本 | 查过的字自动记录；可收藏进生字本，供背诵练习复用 |
| P1-5 | 通假字/异体字联动展示 | 查字页展示关联通假字（tongjia-zi.json）与异体字（yiti-zi.json），点击互跳 |
| P1-6 | 导入大文件后台处理 | MB 级字典导入在后台队列执行，支持进度、取消与失败重试 |

#### P2（Nice to have）

| # | 需求 | 说明 |
|---|------|------|
| P2-1 | 用户导入：Lingoes（.ld2）、Pleco 导出格式 | 格式较封闭/文档不足，视社区需求评估 |
| P2-2 | 词条发音（TTS 或音频） | 依赖原生 TTS，成本低但非核心 |
| P2-3 | 字典云端备份/同步 | 用户字典元信息同步（不含可能侵权的内容本体） |
| P2-4 | 词典内容内嵌搜索 | 全文检索义项/书证内容（FTS5） |

### UI Design Draft（关键页面）

1. **字典入口**：主导航「字典」Tab（或首页入口卡片）。顶部为搜索框（支持字/词/拼音首字母），下方为「最近查询」与「生字本」快捷区。
2. **查字页（DictLookupScreen）**：
   - 顶部：字头大字（可点击发音）、拼音（多音字列出全部读音并高亮语境判定结果）、部首/笔画/异体字行。
   - 中部：释义区，按字典分节（Tab 或折叠卡片：「古汉语」「现代汉语」「我的字典」），每个字典来源显示标签与释义条目（义项编号、词性、书证斜体）。
   - 底部：相关词条（含该字的词语，来自 word-dict.json）。
3. **字典列表页（DictManageScreen）**：卡片列表 = 字典名 + 词条数 + 大小 + 来源标签（内置/导入）+ 排序拖拽手柄；右上角「导入」按钮；用户字典可滑动删除。首项说明当前「默认查询字典」。
4. **导入页（DictImportScreen）**：
   - 步骤 1：选择文件（文件选择器，限定 .mdx/.mdd/.csv/.tsv/.json/.txt）；显示文件大小预估。
   - 步骤 2：解析进度（词条计数实时刷新、进度条、可取消）；解析失败时展示错误行号/原因与「跳过错误继续」选项。
   - 步骤 3：导入完成摘要（词条数、耗时、失败数），并提供「设为默认字典」「立即查一个字试试」。
   - 明示免责声明：用户需确保对导入的字典数据拥有合法使用权。
5. **多音字来源配置（设置内）**：
   - 单选列表：内置规则库（polyphone-rules.json）/ 各已启用字典；
   - 冲突策略预览：给定示例句（如「见」在「风吹草低见牛羊」），展示不同来源下的判音结果差异，帮助用户理解选择的影响。

### Open Questions（待确认，≥3 条）

1. **原生字典数据源选型**：现代义建议 Unicode Unihan（kDefinition 等）+ 通用规范汉字表；古汉语义候选包括「说文解字」开源数字化项目（如 shuowen 项目）、汉典公开页面的爬取合规性待确认、或康熙字典开源数据。**需要确认最终采用哪些数据集及其许可证**（Unihan 为 Unicode License，较安全；其余需逐个核查）。中文释义若需高质量翻译，是否接受社区整理的开源数据（质量参差）？
2. **格式支持清单的分期边界**：MDict + CSV/TSV/JSON/TXT 定为首期，StarDict 定为二期——是否接受？Pleco/Lingoes 是否彻底放弃（其格式逆向解析存在维护与法律风险）？
3. **存储方案**：建议统一 SQLite（候选：op-sqlite / react-native-quick-sqlite，需评估与 RN 0.74.7 + 新架构兼容性）。原生字典是「打包预置 db 文件」还是「首次启动从 asset 导入到用户目录」？后者便于后续 OTA 更新字典数据。
4. **多音字打通的优先级语义**：当字典多音字信息与内置规则库冲突时，默认以哪个为准？建议：用户显式选择的来源 > 内置规则库 > 字典，需产品侧最终拍板。
5. **版权免责**：用户导入字典的合规责任由用户承担，App 内免责声明文案需法务确认。

## 3. 建议的下一步：架构设计需要产出的关键内容

交给架构师的输入要点：

1. **字典数据模型**：统一的 `DictEntry` schema（字头、读音列表、义项、书证、来源元信息），以及各格式（MDict/StarDict/CSV/JSON）→ 内部 schema 的映射规则。
2. **存储与索引设计**：SQLite 表结构（entries、dicts 元数据表）、字头索引（含繁简/异体字归一化查询）、是否启用 FTS5；原生字典预置方式（打包 db vs asset 导入）。
3. **查询引擎接口**：`DictEngine` 的 API 设计（lookup / searchPrefix / searchFuzzy / 聚合多字典），以及与现有 `DictionaryService`、`SearchService` 的整合或替换关系。
4. **导入流水线**：文件选择 → 流式解析（大文件不整体载入内存）→ 分批写入 → 事务与断点续传/取消机制；各格式 parser 的模块边界（便于 P1 扩展 StarDict）。
5. **多音字联动机制**：字典读音数据 → `PinyinService` 判音候选源的注入方式、优先级仲裁规则、以及阅读器提示 UI 的数据流（含 Zustand store 切片设计：dictStore / importQueue）。
6. **性能预算**：启动时惰性打开 db、查询 < 50ms、导入 10MB mdx < 60s（中端机）、内存峰值 < 300MB；JS 侧避免整表加载。
7. **依赖清单评审**：新增原生依赖控制在 2 个以内（sqlite + 文件选择器），MDict 解析建议自研纯 TS 实现以避免重型依赖。
